# Quirk files

Real, publicly offered DICOM files that exercise known encoder bugs, non-conforming headers and edge cases. All were registered on 2026-10-14 as `ext-<source>-<name>` cases by `scripts/sources/quirks.py`. That script lists every file with its URL and quirk; the "Where the files came from" section below says how to fetch them. The binaries live only in the gitignored `formats/*/samples/`, and a download cache sits outside the repository (`~/.cache/shl-quirks`).

The results below are from `check.py --name quirks`, run against `shl-dicom-decode` built from the tree on 2026-10-14.

## Summary

| | Cases |
|---|---|
| Registered | 236 (uncompressed 89, jpeg-lossless 51, jpeg-dct 37, jpeg2000 26, rle 16, jpeg-ls 15, htj2k 2) |
| Pass | 216 (includes 7 `expect=error` cases refused with exit 2) |
| Fail | 18 |
| Unsupported (exit 3) | 2 |
| Crash or timeout | 0 |
| Not registered | 13 (see [Files not registered](#files-not-registered)) |

Of the 18 failures:
- 5 are oracle errors where our decoder is right: [Oracle disputes](#oracle-disputes).
- 4 are disputed oracles where refusing is reasonable.
- 2 are `expect=error` cases that we decode correctly or plausibly.
- 7 are decoder problems:
  - 4 in the CLI (parsing and framing);
  - 1 in CLI normalisation;
  - 1 each in the JPEG lossless and RLE codecs.

One `expect=error` pass, `ext-fodicom-GH1376`, is a mis-filed case that is decodable; see [Failures and their causes](#failures-and-their-causes).

The 2 unsupported cases are a J2K colour-label problem.

## Oracle disputes

These need a ruling in the format's FORMAT.md. In each, our output matches one reference family and the oracle took another.

| Case | Oracle | Ours equals | Evidence |
|---|---|---|---|
| `ext-gdcm-LEADTOOLS_FLOWERS-24-RGB-JpegLossless` | pylibjpeg (GDCM agrees) | dcmtk | The uncompressed original ships in gdcmData (`LEADTOOLS_FLOWERS-24-RGB-Uncompressed.dcm`). Ours equals it exactly; pylibjpeg is off by up to 255. The lossless RGB stream carries a JFIF APP0 marker, and pylibjpeg and GDCM apply YCbCr→RGB because of it. Lossless SOF3 data should not get the JFIF colour transform. |
| `ext-gdcm-DermaColorLossLess` | pylibjpeg | dcmtk | The same JFIF-on-lossless pattern. pylibjpeg's output is magenta; ours is natural skin colour (checked visually). |
| `ext-issue-cornerstone3D_2778-RedactedOriginal` | pylibjpeg (GDCM agrees) | dcmtk | RGB JPEG lossless with Planar Configuration 1. pydicom re-planarises the codec's interleaved output and scrambles it. The reporter's PC=0 copy decodes identically to ours. PS3.5 §8.2.1: Planar Configuration is irrelevant for JPEG. Cornerstone fixed the same bug in PR #2778. |
| `ext-gdcm-HardcopyColor_YBR_RCT_J2K_PC1` | pylibjpeg (GDCM agrees) | opj_decompress | The same Planar Configuration bug for JPEG 2000 (PS3.5 §8.2.4). Ours shows clean red, green and blue text; the oracle is scrambled. |
| `ext-orthanc-Multiframe` | pylibjpeg | GDCM and dcmtk | Corrupt frames ("premature end of data segment"). Two of three references agree with us. |

So `ref_decode`'s pydicom path gets two things wrong, and both may affect other cases:
1. It honours Planar Configuration 1 on JPEG and JPEG 2000 output.
2. Through pylibjpeg and GDCM, it applies the JFIF colour transform to lossless RGB.

These are worth a coordinator rule in `oracle.py`, for example preferring dcmtk or opj_decompress when PC=1 or when a JFIF marker sits on SOF3.

Disputed oracles where our refusal is reasonable; I recommend `expect=error`:

| Case | Problem |
|---|---|
| `ext-fodicom-multiframe` | Frames 126–139 have SOF 121×240 and 121×55 while the data set says 240×240. The dcmtk oracle copies the smaller images unpadded into the full-size buffer, which scrambles them. |
| `ext-gdcm-JPEGNote_bogus` | Rows and Columns say 19789, photometric MONOCHROME1, but the JPEG is 1024×1024 with 3 components. The only oracle is a 391 MB dcmtk buffer with no meaning, so drop it. |
| `ext-gdcm-DCMTK_JPEGExt_12Bits` | Bits Allocated 12 is illegal (PS3.5 §8.1.1). Only dcmtk decodes it; pydicom and our CLI refuse. Make this consistent with `ext-gdcm-JPEGLosslessSeNonZero`, which every reference refuses. |
| `ext-gdcm-MITRA_CORNELL` | The Cornell SSSS=16 encoder bug. dcmtk warns "bad Huffman code" and "premature end", and its output is mostly blank (checked visually). A correct decode needs GDCM's Cornell workaround. |
