# Server storage: SQLite for state, encrypted files in a blob store

Status: design note for `shl-dicom-server`.

Link labels are encrypted in the owner's browser with the owner key, a fresh 96-bit IV, and
AES-256-GCM. The authenticated context is `shl-dicom link label v1:<share-id>`; `ciphertext`
includes the 128-bit tag. The API accepts `labelEncrypted: {v: 1, iv, ciphertext}` (unpadded
base64url), or `null` to clear it, and rejects plaintext `label` writes. The owner browser
decrypts this single label for display and for the SHLink's `label` field; the server never
needs the owner key. Renaming does not alter imaging or invalidate existing links. Copies
already sent retain the label embedded in them.

Legacy plaintext labels are returned to an authenticated owner only until migration. The
browser first verifies its owner key by decrypting the owner Bundle, then encrypts each
legacy label. `PATCH` with `migrateLabel: true` atomically writes the ciphertext and clears
`label`, only while a legacy value still exists; a concurrent rename or clear takes precedence.
Shares that have not been opened with an owner key, and existing database backups, may still
contain old plaintext labels. Public sample labels are intentionally public fixture data.

## Design

- **`catalog.db`** holds what is needed to route a request to the right share (share ids and expiry, link ids, capability tokens) and the reference counts of the stored files.
- **`shares/{sid}.db`** holds everything else about one share: the control-token hash, links and passcode counters, allowed-file lists, the owner and link Bundles, the list of encrypted files, uploads in progress, and the access log.
- **The blob store** holds the finished encrypted files (one per study, spec/README.md §11.1), exactly as the sharer uploaded them. It is a server setting:
  - **local files** (the default): `{data-dir}/blobs/{key}`;
  - **an S3 bucket** (any S3-compatible service): objects `{prefix}{key}` in a private bucket.
- **Uploads in progress** are staged on local disk in `shares/{sid}/{fileId}.part`, whichever store holds finished files.

SQLite stays on local disk with either store, so passcode attempts, the link and file checks and the access log stay atomic and local. Only the finished files move.

A file's **storage key** is drawn at random for each upload: 16 random bytes as base64url, plus `.bin`. A key is never reused, and it names no share or file, so a presigned URL reveals neither. A cloned share names the same keys, so cloning copies no bytes; the catalog counts how many file rows name each key, and a blob is deleted when the count reaches zero.

Every path the server opens is built from a `sid` and a `fileId` that match `^[A-Za-z0-9_-]{22}$`. The `sid` was generated by the server and found in the catalog. The `fileId` is checked against that pattern before any file is touched, and it is listed in the share's database before it is served.

## Why

**Atomic state changes.** SQLite transactions and constraints cover the rules that must not race:
- the passcode attempt counter;
- `409` when deleting a file that a link still lists;
- links that name only files that exist.

**Large files.** Encrypted files can be many gigabytes (a whole-slide image is often over 1 GB). They are written as they arrive and read by range, so neither uploads nor reads hold a file in memory.

**Object storage.** Large shares and many of them can live in a bucket instead of on the server's disk, while the protocol stays the same: readers always ask the server, which checks the link before it serves or redirects (below).

**Writes in parallel.** One database per share means uploads to different shares don't queue behind each other.

## Layout

```
{data-dir}/
├── catalog.db            (+ -wal, -shm)
├── samples/              the server's sample: *.tgz, sample.json, reports.json
├── blobs/                finished files, when the local store is used
│   └── {key}             a random storage key, such as 3q2-7wAAAAA_lH9AAQIDBA.bin
└── shares/
    ├── {sid}.db          (+ -wal, -shm)
    ├── {sid}/
    │   ├── {fileId}.part     staged bytes of an upload in progress
    │   └── {fileId}.part.{n} part n on its way to S3
    └── …
```

`sid`, `lid` and capability tokens are random base64url strings generated by the server: a `sid` is 16 random bytes (22 characters); a `lid` and a capability token are 32 random bytes (43 characters), since the link's `url` must carry at least 256 bits of entropy.

## Schemas

### catalog.db

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE shares (
  sid         TEXT PRIMARY KEY,
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER,                 -- NULL for the server's sample
  read_only   INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE links (
  lid  TEXT PRIMARY KEY,
  sid  TEXT NOT NULL REFERENCES shares(sid) ON DELETE CASCADE
);

CREATE TABLE caps (
  token       TEXT PRIMARY KEY,
  lid         TEXT NOT NULL REFERENCES links(lid) ON DELETE CASCADE,
  expires_at  INTEGER NOT NULL
);
CREATE INDEX caps_expiry ON caps(expires_at);

-- How many file rows (in any share) name each blob.
CREATE TABLE blobs (
  storage_key  TEXT PRIMARY KEY,           -- random, drawn for the upload
  ref_count    INTEGER NOT NULL
);

-- Blobs no file names any more, and unfinished multipart uploads, to remove from the store.
CREATE TABLE trash (
  storage_key  TEXT NOT NULL,
  upload_id    TEXT                        -- set: abort this multipart upload; NULL: delete the blob
);
```

Capability tokens live in the catalog because `/cap/{token}/…` has to be routed before the server knows which share it belongs to.

### shares/{sid}.db

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE share (
  id                  INTEGER PRIMARY KEY CHECK (id = 1),   -- single row
  control_token_hash  BLOB NOT NULL,                        -- SHA-256 of the token
  owner_bundle        BLOB,                                 -- owner.jwe, opaque
  owner_updated_at    INTEGER
);

-- Complete encrypted files. The bytes are in the blob store under storage_key (random, never reused), which a cloned
-- share shares with its source.
CREATE TABLE files (
  file_id      TEXT PRIMARY KEY,           -- 22-char base64url
  storage_key  TEXT NOT NULL,
  size         INTEGER NOT NULL,           -- ciphertext length C
  uploaded_at  INTEGER NOT NULL
);

-- Uploads in progress. Upload-Offset = flushed_bytes + the size of shares/{sid}/{file_id}.part.
CREATE TABLE uploads (
  file_id        TEXT PRIMARY KEY,
  storage_key    TEXT NOT NULL,            -- the blob it will become
  size           INTEGER NOT NULL,         -- Upload-Length; -1 until it is given
  s3_upload_id   TEXT,                     -- the S3 multipart upload, when there is one
  flushed_bytes  INTEGER NOT NULL DEFAULT 0,
  started_at     INTEGER NOT NULL
);

-- Parts already sent to S3 for an upload in progress.
CREATE TABLE upload_parts (
  file_id   TEXT NOT NULL REFERENCES uploads(file_id) ON DELETE CASCADE,
  part_num  INTEGER NOT NULL,              -- 1-based S3 part number
  etag      TEXT NOT NULL,
  size      INTEGER NOT NULL,
  PRIMARY KEY (file_id, part_num)
) WITHOUT ROWID;

CREATE TABLE links (
  lid                 TEXT PRIMARY KEY,
  label               TEXT, -- legacy only; removed when the owner browser migrates it
  label_encrypted     TEXT, -- {v, iv, ciphertext}; AES-256-GCM under the owner key
  long_lived          INTEGER NOT NULL,
  online              INTEGER NOT NULL DEFAULT 1,
  exp                 INTEGER,
  passcode_salt       BLOB,                -- NULL means no passcode (U mode)
  passcode_hash       BLOB,
  remaining_attempts  INTEGER,
  bundle              BLOB,                -- bundle.jwe, opaque
  bundle_etag         TEXT,
  bundle_updated_at   INTEGER,
  created_at          INTEGER NOT NULL
);

CREATE TABLE link_files (
  lid      TEXT NOT NULL REFERENCES links(lid) ON DELETE CASCADE,
  file_id  TEXT NOT NULL REFERENCES files(file_id),    -- no cascade: blocks deletion (409)
  PRIMARY KEY (lid, file_id)
) WITHOUT ROWID;

CREATE TABLE access_log (
  ts         INTEGER NOT NULL,
  lid        TEXT,
  method     TEXT NOT NULL,
  path       TEXT NOT NULL,
  range      TEXT,
  status     INTEGER NOT NULL,
  bytes      INTEGER NOT NULL,
  recipient  TEXT
);
CREATE INDEX access_ts ON access_log(ts);
```

- **`link_files.file_id` has no cascade.** Deleting a file that a link still lists fails with a foreign key error, which the API returns as `409 Conflict`.
- **A link can list only complete files**: `link_files` references `files`, and a file is in `files` only once all its bytes are in the store.

## Request flows

**`GET /shl/{lid}/{fileId}.bin` with `Range: bytes=a-b`**
1. Check the shape of `lid` and `fileId`; anything else gets `404`.
2. Catalog lookup `lid → sid`. If missing, `404`. Open (or reuse) `shares/{sid}.db`.
3. Check the link: it exists, is online and not expired, has no passcode, and has a `link_files` row for `fileId`. Otherwise `404`.
4. Read `size` and `storage_key` from `files`, clamp the range to `[0, size)`, and reject multi-range requests (`416`).
5. `HEAD` is answered here, with the same status and headers and no body, in every mode (a presigned URL is for `GET` only). For `GET`, deliver the range by the store's read mode:
   - **local files**, or **S3 in `proxy` mode**: read the range (a seek in the file, or an S3 `GetObject` with `Range`) and stream it. Respond `206` with `Content-Range: bytes a-b/size`, `Content-Type: application/octet-stream`, no `Content-Encoding`, and `Access-Control-Allow-Origin: *`.
   - **S3 in `redirect` mode**: respond `307` with `Location` set to a presigned `GetObject` URL valid for 60 s, `Cache-Control: no-store` and `Access-Control-Allow-Origin: *`. The browser repeats its `Range` request there; the bucket answers `206`. A URL signed before the link is revoked stays usable until it expires, so revocation takes effect within 60 s in this mode.

   A blob missing from the store is a `404`. In `proxy` mode, S3 must answer `206` (or `200` when the range is the whole file); anything else is a `502`. Store errors are logged; clients get no detail, and presigned URLs never appear in logs or error responses.
6. Append to `access_log` and notify SSE subscribers. In redirect mode `bytes` is the requested length.

The checks in steps 1–4 run for every read in both modes, so revoking a link, taking it offline or deleting a share stops reads at once. A presigned URL the server has already handed out stays usable until it expires (60 s); the server reuses a presigned URL for the same blob for at most 30 s.

**`GET /shl/{lid}/bundle.jwe`.** Steps 1–3 as above, without the file check. Then return `links.bundle`, with `bundle_etag` as the `ETag` and `304` for a matching `If-None-Match`.

**`POST /shl/{lid}` (passcode).** In one transaction on the share database:

```sql
UPDATE links SET remaining_attempts = remaining_attempts - 1
 WHERE lid = ? AND remaining_attempts > 0
 RETURNING remaining_attempts;
```

- **No row returned:** the link is exhausted, so `404`.
- **A row is returned:** compare the passcode hash.
  - **Match:** restore the attempt in the same transaction, then mint a capability token and insert it into `caps` in the catalog.
  - **Mismatch:** commit and return `401` with the remaining count.

Taking an attempt before checking means concurrent wrong guesses can never exceed the limit.

**`GET /cap/{token}/…`.** Catalog lookup `token → lid → sid`, with `expires_at > now`. Then the same as the `/shl` flows, without the passcode check.

## Write flows

**Uploading a file.** The upload follows the IETF resumable uploads draft (PLAN.md §5.2): `PUT` with `Upload-Complete` creates it, `HEAD` reports `Upload-Offset`, `PATCH` appends. A `PUT` without `Upload-Complete` sends the whole file in one request.
1. Authenticate: the SHA-256 of the bearer token must match `share.control_token_hash`.
2. Allow one request at a time per file; another gets `409`.
3. Creating: check the share's limits against `Upload-Length`, draw a storage key, and insert an `uploads` row. With the S3 store and more than 8 MiB, or no `Upload-Length`, start a multipart upload and record its id.
   - Without `Upload-Length`, the row's size is -1 until an append gives it. Then the limits are checked against it, and it is fixed: a different one later gets `400`.
4. Appending: `Upload-Offset` must equal `flushed_bytes` plus the size of `{fileId}.part`; otherwise `409` with the right `Upload-Offset`.
5. Stream the body to the end of `{fileId}.part` (a new one, if there is none).
   - The connection drops, or no byte arrives for 30 s: keep what arrived. The client asks where to continue.
   - The body would go past `Upload-Length`, or `Upload-Complete: ?1` arrives before the last byte: truncate back to where the request started and answer `400`.
   - No `Upload-Length` yet, and the body would take the share past its byte limit (counting other uploads of unknown length at what they have): truncate back to where the request started and answer `413`.
6. With a multipart upload, once the staged file reaches the part size it is sent as the next part:
   1. rename `{fileId}.part` to `{fileId}.part.{n}`; from here its bytes don't count toward `Upload-Offset`;
   2. send it as part `n`;
   3. record the part in `upload_parts` and add its size to `flushed_bytes`, in one transaction;
   4. delete `{fileId}.part.{n}`.

   If sending fails, the request gets `502` and the offset is where the last recorded part ended; the client asks `HEAD` and sends the rest again. A crash anywhere in these steps leaves the same offset. A leftover `{fileId}.part.{n}` never counts, and the next send of part `n` replaces it.

   The part size is `max(8 MiB, Upload-Length / 9,500)` rounded up to 64 KiB, so parts are at least S3's 5 MiB and never more than 10,000. Until `Upload-Length` is given, it is 16 MiB (10,000 parts: 160 GiB). The staged file stays under one part plus one append.
7. When the last byte arrives with `Upload-Complete: ?1` (without `Upload-Length` ever given, the length is where it ends):
   - local store: sync the staged file and rename it into `blobs/`;
   - S3, multipart: send the rest as the last part, then complete the multipart upload;
   - S3, 8 MiB or less: one `PutObject` from the staged file.

   Then insert the `files` row, add a reference to the blob, and delete the `uploads` row.

A link can name the file only after step 7.

**Cloning a share.** The new share gets the same `files` rows, with the source's storage keys, and each blob gains a reference. No bytes are copied, whatever the size. The source's database stays locked until every reference is added, and deleting a file drops its reference under the same lock, so a file deleted during a clone can't lose a blob the clone names. Lock order: the source share, the new share, then the catalog.

**Deleting a file or a share.** Each deleted `files` row drops a reference; a blob with none goes to `trash`. Each unfinished upload with a multipart id goes to `trash` too, and its staged files are deleted. A background task empties the trash (deleting blobs, aborting multipart uploads) shortly after, and every minute. An item leaves the trash only once the store confirms it is gone; a blob or upload that is already gone (`404`, `NoSuchUpload`) counts as gone.

**The server's sample.** `shl-dicom-server seed` (run at deploy time) packs `samples/*.tgz` one record at a time into staged files and puts each into the store (multipart, from the file, for large ones), with no quota. It adds the DiagnosticReports in `samples/reports.json` to the sample's Bundle. `serve` only loads what `seed` made.

**Creating a link.**
1. Insert the link and its `link_files` rows into the share database, and commit.
2. Then insert `lid → sid` into the catalog.

**Deleting a link.**
1. Delete the catalog row first. That stops routing immediately and cascades to `caps`.
2. Then delete the row in the share database, which cascades to `link_files`.

**Rule for changes that touch the catalog and a share:**
- When creating, write the share first and the catalog last.
- When deleting, write the catalog first and the share last.

The catalog therefore never routes to something incomplete or already gone. Anything a crash leaves behind has no catalog entry pointing at it, and the sweep removes it.

**Expiring or deleting a share.**
1. Delete the catalog `shares` row, which cascades to its links and caps.
2. Release its files' blobs and trash its unfinished uploads, as above.
3. Close any open connection to the share database, and delete `{sid}.db`, `{sid}.db-wal`, `{sid}.db-shm` and the staging directory `{sid}/`.

## Sweep

On start, and before a share is created:
- delete expired catalog `caps` rows;
- delete expired shares, as above;
- delete any `shares/{sid}.db` file or `shares/{sid}/` directory whose `sid` has no catalog row.

On start, and every 10 minutes: drop uploads that started more than 24 hours ago (with or without a length) and have no request in progress. That removes their `uploads` row, their staged files and their multipart upload.

**For S3, also add a lifecycle rule to the bucket** that aborts incomplete multipart uploads after 1 day (`AbortIncompleteMultipartUpload`, `DaysAfterInitiation: 1`). It removes parts the server lost track of, for example after its data directory was lost.

## Settings

Server settings, from `serve` (and `seed`) flags or the environment.

**Address**

| Setting | Environment | Default | Meaning |
|---|---|---|---|
| `--public-origin` | `SHL_PUBLIC_ORIGIN` | unset | The server's public origin (for example `https://shlink-dicom.exe.xyz`). When set, it is the only source of absolute URLs: the sample's links, the `/sample` redirect, manifest and link URLs. Unset, they come from `X-Forwarded-Proto` and `X-Forwarded-Host` (else `Host`), which clients can forge; run without it only behind a proxy that overwrites those headers. |

**Limits**

| Setting | Environment | Default | Meaning |
|---|---|---|---|
| `--max-share-bytes` | `SHL_MAX_SHARE_BYTES` | 0 (no limit) | Encrypted bytes one share may hold, counting uploads in progress (for example `20G`) |
| `--max-total-bytes` | `SHL_MAX_TOTAL_BYTES` | 0 (no limit) | Encrypted bytes all shares together may hold: each stored file once (a clone adds none), plus uploads in progress at their declared length. Over it, an upload is refused with `507` (`QUOTA_SERVER_FULL`) |
| `--max-share-files` | `SHL_MAX_SHARE_FILES` | 0 (no limit) | Encrypted files one share may hold |
| `--max-shares` | `SHL_MAX_SHARES` | 256 | Shares at once, not counting the sample; 0 for no limit |
| `--max-chunk-bytes` | `SHL_MAX_CHUNK_BYTES` | `64M` | Largest append (`Upload-Limit: max-append-size`) |
| `--cap-ttl-secs` | `SHL_CAP_TTL_SECS` | 3600 | Lifetime of a passcode link's capability URL, at most 3600 (the SHL spec's limit) |

JSON and JWE request bodies are capped at 32 MiB, and a Bundle (`owner.jwe` or a link's `bundle.jwe`) at 16 MiB. Requests that need no token (creating a share, asking for a manifest) are capped at 16 KiB. A share may have 100 links. The server handles 512 requests at once; past that it answers `503` with `Retry-After`. File bodies stream to the staged file and have no body cap.

**Blob store.** Without `--s3-bucket`, files are kept in `{data-dir}/blobs/`.

| Setting | Environment | Default | Meaning |
|---|---|---|---|
| `--s3-bucket` | `SHL_S3_BUCKET` | unset | The bucket; setting it selects the S3 store |
| `--s3-endpoint` | `SHL_S3_ENDPOINT` | AWS, for the region | Endpoint URL of an S3-compatible service |
| `--s3-region` | `SHL_S3_REGION` | `us-east-1` | Region, for request signing |
| `--s3-access-key-id` | `AWS_ACCESS_KEY_ID` | | Credentials |
| `--s3-secret-access-key` | `AWS_SECRET_ACCESS_KEY` | | |
| `--s3-prefix` | `SHL_S3_PREFIX` | empty | Prefix for object keys inside the bucket |
| `--s3-read-mode` | `SHL_S3_READ_MODE` | `proxy` | `proxy`: the server streams ranges from S3. `redirect`: `307` to a presigned URL valid for 60 s |
| `--s3-path-style` | `SHL_S3_PATH_STYLE` | false | Path-style URLs (`https://host/bucket/key`), as MinIO and similar services need |

**The bucket stays private.** Objects are never public; readers reach them only through the server's checks, either streamed by the server or by a presigned URL that lasts 60 s.

**Bucket CORS for `redirect` mode.** A browser following a cross-origin `307` sends `Origin: null` to the bucket. The bucket's CORS policy therefore needs `AllowedOrigins: ["*"]`, `AllowedMethods: ["GET", "HEAD"]`, `AllowedHeaders: ["Range"]`, `ExposeHeaders: ["Content-Range", "Content-Length", "Accept-Ranges", "ETag"]`, and no credentials. `proxy` mode needs no bucket CORS.

## Connections

- **Catalog:** one connection, kept open.
- **Share databases:** opened on demand and kept in an LRU of 64. Each connection sits behind a mutex.
- **Pragmas on every open:** `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`.
- **SQLite version:** `RETURNING` needs SQLite 3.35 or later.
- **S3:** requests are signed locally (SigV4, `rusty-s3`) and sent with `reqwest`; uploads and proxied reads stream.

## Path safety

The server opens:
- `{data-dir}/catalog.db`;
- `{data-dir}/shares/{sid}.db` and files in `{data-dir}/shares/{sid}/`, where `sid` comes from a catalog row and matches `^[A-Za-z0-9_-]{22}$`;
- `{fileId}.part` and `{fileId}.part.{n}` in that directory, where `fileId` matches `^[A-Za-z0-9_-]{22}$`;
- `{data-dir}/blobs/{key}`, where `key` was drawn by the server and matches `^[A-Za-z0-9_-]{22}\.bin$`.

S3 object keys are `{prefix}{key}`.

The data directory is resolved once at startup. The process runs as an unprivileged user that owns only that directory. Under systemd, also set `ProtectSystem=strict`, `ReadWritePaths={data-dir}`, `NoNewPrivileges=yes` and `PrivateTmp=yes`.

## Tests

`cargo test -p shl-dicom-server` runs against the local store. With `SHL_TEST_S3_BUCKET`, `SHL_TEST_S3_ENDPOINT`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `SHL_TEST_S3_READ_MODE` (`proxy` or `redirect`) set, the same tests run against S3 (for example a local MinIO). They cover:
1. range reads of single and spanning records, with exact `Content-Range`;
2. resumable uploads: creation, `HEAD` offset retrieval, an append at the wrong offset (`409` with `Upload-Offset` and the mismatching-upload-offset problem), an early `Upload-Complete: ?1` (`400`), and publication after the last append;
3. a 20 MiB upload in 3 MiB appends with one cut off mid-body, continued from `HEAD`'s offset; on S3 it goes up as multipart parts, and ranges across part boundaries read back exact;
4. size checks: a body that doesn't match its declared size leaves nothing behind;
5. per-share limits (`413`);
6. `409` when deleting a file a link still lists;
7. passcode attempts under concurrency;
8. clones share blobs by reference: the blob outlives its source share and is deleted with the last share that names it, and storage keys name no share;
9. redirect mode: a `307` to a presigned URL that serves the range and names no share, `HEAD` answered by the server, and no redirect after the link is revoked;
10. deleting an unfinished upload aborts its S3 multipart upload;
11. a part that fails on its way to the store: `502` without the store's detail, `HEAD` back at the last stored part (a leftover `.part.{n}` not counted), and the upload finished from there;
12. a blob whose delete fails stays in the trash and goes on the next try;
13. the sweep drops uploads older than 24 hours and keeps recent ones;
14. a blob missing from the store reads as `404`;
15. share expiry and parallel uploads;
16. an upload begun without a length: 23 MiB in appends, parts sent as they fill, the length given with the last append; one completed without a length; a length once given is fixed;
17. the share's byte limit while the length is unknown: an append that would pass it gets `413` and leaves nothing, other uploads of unknown length count what they have, and a length given too large gets `413`.
