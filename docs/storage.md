# Server storage: SQLite for state, series files on disk

Status: design note for `shl-dicom-server`.

## Design

- **`catalog.db`** holds only what is needed to route a request to the right share: share ids and expiry, link ids, and capability tokens.
- **`shares/{sid}.db`** holds everything else about one share: the control-token hash, links and passcode counters, allowed-file lists, the owner and link Bundles, the list of series files, uploads in progress, and the access log.
- **`shares/{sid}/{fileId}.bin`** are the encrypted series files, exactly as the sharer uploaded them. An upload in progress is `{fileId}.part` in the same directory.

Every path the server opens is built from a `sid` and a `fileId` that match `^[A-Za-z0-9_-]{22}$`. The `sid` was generated by the server and found in the catalog. The `fileId` is checked against that pattern before any file is touched, and it is listed in the share's database before it is served.

## Why

**Atomic state changes.** SQLite transactions and constraints cover the rules that must not race:
- the passcode attempt counter;
- `409` when deleting a file that a link still lists;
- links that name only files that exist.

**Large files.** Series files can be many gigabytes (a whole-slide image is often over 1 GB). On disk they are written as they arrive and read with a seek, so neither uploads nor range reads hold a file in memory. Range reads stream from the file.

**Freeing space.** Deleting or expiring a share removes its database and its directory, and the space is free at once.

**Writes in parallel.** One database per share means uploads to different shares don't queue behind each other.

## Layout

```
{data-dir}/
├── catalog.db            (+ -wal, -shm)
├── samples/              the server's sample: *.tgz, sample.json, reports.json
└── shares/
    ├── {sid}.db          (+ -wal, -shm)
    ├── {sid}/
    │   ├── {fileId}.bin
    │   └── {fileId}.part     while an upload is incomplete
    └── …
```

`sid`, `lid` and capability tokens are random base64url strings generated by the server: 22 characters for ids, 43 for tokens.

## Schemas

### catalog.db

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE shares (
  sid         TEXT PRIMARY KEY,
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER,                 -- NULL for the server's sample
  read_only   INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE links (
  lid  TEXT PRIMARY KEY,
  sid  TEXT NOT NULL REFERENCES shares(sid) ON DELETE CASCADE
);

CREATE TABLE caps (
  token       TEXT PRIMARY KEY,
  lid         TEXT NOT NULL REFERENCES links(lid) ON DELETE CASCADE,
  expires_at  INTEGER NOT NULL
);
CREATE INDEX caps_expiry ON caps(expires_at);
```

Capability tokens live in the catalog because `/cap/{token}/…` has to be routed before the server knows which share it belongs to.

### shares/{sid}.db

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE share (
  id                  INTEGER PRIMARY KEY CHECK (id = 1),   -- single row
  control_token_hash  BLOB NOT NULL,                        -- SHA-256 of the token
  owner_bundle        BLOB,                                 -- owner.jwe, opaque
  owner_updated_at    INTEGER
);

-- Complete series files; each is shares/{sid}/{file_id}.bin.
CREATE TABLE series_files (
  file_id      TEXT PRIMARY KEY,           -- 22-char base64url
  size         INTEGER NOT NULL,           -- ciphertext length C
  uploaded_at  INTEGER NOT NULL
);

-- Uploads in progress: the declared size of each shares/{sid}/{file_id}.part.
CREATE TABLE uploads (
  file_id     TEXT PRIMARY KEY,
  size        INTEGER NOT NULL,
  started_at  INTEGER NOT NULL
);

CREATE TABLE links (
  lid                 TEXT PRIMARY KEY,
  label               TEXT,
  long_lived          INTEGER NOT NULL,
  online              INTEGER NOT NULL DEFAULT 1,
  exp                 INTEGER,
  passcode_salt       BLOB,                -- NULL means no passcode (U mode)
  passcode_hash       BLOB,
  remaining_attempts  INTEGER,
  bundle              BLOB,                -- bundle.jwe, opaque
  bundle_etag         TEXT,
  bundle_updated_at   INTEGER,
  created_at          INTEGER NOT NULL
);

CREATE TABLE link_files (
  lid      TEXT NOT NULL REFERENCES links(lid) ON DELETE CASCADE,
  file_id  TEXT NOT NULL REFERENCES series_files(file_id),    -- no cascade: blocks deletion (409)
  PRIMARY KEY (lid, file_id)
) WITHOUT ROWID;

CREATE TABLE access_log (
  ts         INTEGER NOT NULL,
  lid        TEXT,
  method     TEXT NOT NULL,
  path       TEXT NOT NULL,
  range      TEXT,
  status     INTEGER NOT NULL,
  bytes      INTEGER NOT NULL,
  recipient  TEXT
);
CREATE INDEX access_ts ON access_log(ts);
```

- **`link_files.file_id` has no cascade.** Deleting a series file that a link still lists fails with a foreign key error, which the API returns as `409 Conflict`.
- **A link can list only complete files**: `link_files` references `series_files`, and a file is in `series_files` only once all its bytes are on disk.

## Request flows

**`GET /shl/{lid}/{fileId}.bin` with `Range: bytes=a-b`**
1. Check the shape of `lid` and `fileId`; anything else gets `404`.
2. Catalog lookup `lid → sid`. If missing, `404`. Open (or reuse) `shares/{sid}.db`.
3. Check the link: it exists, is online and not expired, has no passcode, and has a `link_files` row for `fileId`. Otherwise `404`.
4. Read `size` from `series_files`, clamp the range to `[0, size)`, and reject multi-range requests.
5. Open `shares/{sid}/{fileId}.bin`, seek to `a`, and stream `b − a + 1` bytes. Respond `206` with `Content-Range: bytes a-b/size`, `Content-Type: application/octet-stream`, no `Content-Encoding`, and `Access-Control-Allow-Origin: *`.
6. Append to `access_log` and notify SSE subscribers.

**`GET /shl/{lid}/bundle.jwe`.** Steps 1–3 as above, without the file check. Then return `links.bundle`, with `bundle_etag` as the `ETag` and `304` for a matching `If-None-Match`.

**`POST /shl/{lid}` (passcode).** In one transaction on the share database:

```sql
UPDATE links SET remaining_attempts = remaining_attempts - 1
 WHERE lid = ? AND remaining_attempts > 0
 RETURNING remaining_attempts;
```

- **No row returned:** the link is exhausted, so `404`.
- **A row is returned:** compare the passcode hash.
  - **Match:** restore the attempt in the same transaction, then mint a capability token and insert it into `caps` in the catalog.
  - **Mismatch:** commit and return `401` with the remaining count.

Taking an attempt before checking means concurrent wrong guesses can never exceed the limit.

**`GET /cap/{token}/…`.** Catalog lookup `token → lid → sid`, with `expires_at > now`. Then the same as the `/shl` flows, without the passcode check.

## Write flows

**Uploading a series file (`PUT /api/shares/{sid}/files/{fileId}.bin`).** The client sends the whole file in one request, or chunks with `Content-Range: bytes a-b/total` (PLAN.md §5.2).
1. Authenticate: the SHA-256 of the bearer token must match `share.control_token_hash`.
2. Allow one request at a time per file.
3. A new upload: check the share's limits against the declared total, insert an `uploads` row, and start `{fileId}.part`. A whole-file request always starts over.
4. A chunk must start where `{fileId}.part` ends; otherwise `409` with `received`.
5. Stream the body to the end of `{fileId}.part`. If the body is longer or shorter than declared, truncate the file back to where the request started.
6. When the last byte arrives, sync the file, rename it to `{fileId}.bin`, insert the `series_files` row and delete the `uploads` row.

A link can name the file only after step 6.

**Cloning a share.** The new share's directory gets a hard link to each series file (a copy where the file system can't link), and the same `series_files` rows.

**The server's sample.** At startup the seed packs `samples/*.tgz`, writes each series file the same way and records it, with no quota. It adds the DiagnosticReports in `samples/reports.json` to the sample's Bundle.

**Creating a link.**
1. Insert the link and its `link_files` rows into the share database, and commit.
2. Then insert `lid → sid` into the catalog.

**Deleting a link.**
1. Delete the catalog row first. That stops routing immediately and cascades to `caps`.
2. Then delete the row in the share database, which cascades to `link_files`.

**Rule for changes that touch the catalog and a share:**
- When creating, write the share first and the catalog last.
- When deleting, write the catalog first and the share last.

The catalog therefore never routes to something incomplete or already gone. Anything a crash leaves behind has no catalog entry pointing at it, and the sweep removes it.

**Expiring or deleting a share.**
1. Delete the catalog `shares` row, which cascades to its links and caps.
2. Close any open connection to the share database.
3. Delete `{sid}.db`, `{sid}.db-wal`, `{sid}.db-shm` and the `{sid}/` directory.

## Sweep

On start, and before a share is created:
- delete expired catalog `caps` rows;
- delete expired shares, as above;
- delete any `shares/{sid}.db` file or `shares/{sid}/` directory whose `sid` has no catalog row.

## Limits

Server settings, from `serve` flags or the environment:

| Setting | Environment | Default | Meaning |
|---|---|---|---|
| `--max-share-bytes` | `SHL_MAX_SHARE_BYTES` | 0 (no limit) | Encrypted bytes one share may hold, counting uploads in progress (for example `20G`) |
| `--max-share-files` | `SHL_MAX_SHARE_FILES` | 0 (no limit) | Series files one share may hold |
| `--max-shares` | `SHL_MAX_SHARES` | 256 | Shares at once, not counting the sample; 0 for no limit |
| `--max-chunk-bytes` | `SHL_MAX_CHUNK_BYTES` | `64M` | Largest upload chunk |

JSON and JWE request bodies (links, Bundles, `owner.jwe`) are capped at 32 MiB. Series file bodies stream to disk and have no body cap.

## Connections

- **Catalog:** one connection, kept open.
- **Share databases:** opened on demand and kept in an LRU of 64. Each connection sits behind a mutex.
- **Pragmas on every open:** `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`.
- **SQLite version:** `RETURNING` needs SQLite 3.35 or later.

## Path safety

The server opens:
- `{data-dir}/catalog.db`;
- `{data-dir}/shares/{sid}.db` and files in `{data-dir}/shares/{sid}/`, where `sid` comes from a catalog row and matches `^[A-Za-z0-9_-]{22}$`;
- `{fileId}.bin` and `{fileId}.part` in that directory, where `fileId` matches `^[A-Za-z0-9_-]{22}$`.

The data directory is resolved once at startup. The process runs as an unprivileged user that owns only that directory. Under systemd, also set `ProtectSystem=strict`, `ReadWritePaths={data-dir}`, `NoNewPrivileges=yes` and `PrivateTmp=yes`.

## Tests

`cargo test -p shl-dicom-server` covers:
1. range reads of single and spanning records, from disk, with exact `Content-Range`;
2. chunked uploads: a chunk that skips ahead gets `409` with `received`, the status `GET` reports progress, and the file is published after the last chunk;
3. size checks: a body that doesn't match its declared size leaves nothing behind;
4. per-share limits (`413`);
5. `409` when deleting a file a link still lists;
6. passcode attempts under concurrency;
7. clones, share expiry and parallel uploads.
