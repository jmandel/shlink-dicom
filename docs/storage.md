# Server storage: a SQLite catalog plus one SQLite file per share

Status: design note for `shl-dicom-server`. It replaces the `meta.json` + loose files layout in PLAN.md §1 and §2.

## Decision

All server state, including the encrypted series files, lives in SQLite:

- **`catalog.db`** holds only what is needed to route a request to the right share: share ids and expiry, link ids, and capability tokens.
- **`shares/{sid}.db`** holds everything else for one share: the control-token hash, links and passcode counters, allowed-file lists, the owner and link Bundles, the series files stored as 64 KiB records, and the access log.

The server never opens a filesystem path built from request text. Every file it opens is either `catalog.db` or `shares/{sid}.db`, for a `sid` the server generated and then found in the catalog.

## Why

**Path safety.** The receiver-facing routes take ids and file names from URLs. With loose files on disk, the defences are:
- strict validation of ids and names;
- never using a generic static-file handler;
- keeping `meta.json` out of any served directory;
- refusing symlinks;
- tests for every encoding trick.

Each is easy to get wrong once. With records in a database, a request names a row, not a path, so there is no path to traverse. The only paths are the catalog and one file per share, and neither is derived from what the client sent.

**Atomic state changes.** Several rules in the plan are about doing several things at once without races:
- the passcode attempt counter;
- `409` when deleting a file that a link still lists;
- publishing new files before a new Bundle;
- an upload that must never be visible half-written.

In SQLite these are transactions and constraints:
- The passcode counter is one statement: `UPDATE … SET remaining = remaining - 1 WHERE … AND remaining > 0 RETURNING remaining`.
- The `409` is a foreign key violation.
- An upload is visible only after it commits.

**Freeing space.** One database for everything only shrinks after `VACUUM`, which is slow on a large file. With one file per share, deleting or expiring a share removes a file, and the space is free at once. Sandbox shares expire often, so this matters here.

**Writes in parallel.** SQLite allows one writer per database file. One file per share means uploads to different shares don't queue behind each other.

**Isolation and portability.** A bug in a query can only return rows from the share file it opened. A share's complete state is one file that can be copied, inspected with the `sqlite3` tool, or handed over.

**Range reads are cheap because of the format.** Series files are already made of fixed 65,536-byte records (PROPOSAL.md §9). Storing one record per row turns a byte-range request into an indexed range query over whole rows. The server never parses or decrypts anything; it works only in ciphertext byte offsets.

## Layout

```
{data-dir}/
├── catalog.db            (+ -wal, -shm)
└── shares/
    ├── {sid}.db          (+ -wal, -shm)
    └── …
```

`sid`, `lid` and capability tokens are random base64url strings generated by the server: 22 characters for ids, 43 for tokens.

## Schemas

### catalog.db

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE shares (
  sid         TEXT PRIMARY KEY,
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER,                 -- sandbox TTL; NULL for permanent
  read_only   INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE links (
  lid  TEXT PRIMARY KEY,
  sid  TEXT NOT NULL REFERENCES shares(sid) ON DELETE CASCADE
);

CREATE TABLE caps (
  token       TEXT PRIMARY KEY,
  lid         TEXT NOT NULL REFERENCES links(lid) ON DELETE CASCADE,
  expires_at  INTEGER NOT NULL
);
CREATE INDEX caps_expiry ON caps(expires_at);
```

Capability tokens live in the catalog because `/cap/{token}/…` has to be routed before the server knows which share it belongs to. Deleting a link deletes its tokens through the cascade.

### shares/{sid}.db

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE share (
  id                  INTEGER PRIMARY KEY CHECK (id = 1),   -- single row
  control_token_hash  BLOB NOT NULL,                        -- SHA-256 of the token
  owner_bundle        BLOB,                                 -- owner.jwe, opaque
  owner_updated_at    INTEGER
);

CREATE TABLE series_files (
  file_id      TEXT PRIMARY KEY,           -- 22-char base64url
  size         INTEGER NOT NULL,           -- ciphertext length C
  uploaded_at  INTEGER NOT NULL
);

CREATE TABLE series_records (
  file_id  TEXT    NOT NULL REFERENCES series_files(file_id) ON DELETE CASCADE,
  idx      INTEGER NOT NULL,
  bytes    BLOB    NOT NULL,               -- 65,536 bytes except the last
  PRIMARY KEY (file_id, idx)
) WITHOUT ROWID;

CREATE TABLE links (
  lid                 TEXT PRIMARY KEY,
  label               TEXT,
  long_lived          INTEGER NOT NULL,
  online              INTEGER NOT NULL DEFAULT 1,
  exp                 INTEGER,
  passcode_salt       BLOB,                -- NULL means no passcode (U mode)
  passcode_hash       BLOB,
  remaining_attempts  INTEGER,
  bundle              BLOB,                -- bundle.jwe, opaque
  bundle_etag         TEXT,
  bundle_updated_at   INTEGER,
  created_at          INTEGER NOT NULL
);

CREATE TABLE link_files (
  lid      TEXT NOT NULL REFERENCES links(lid) ON DELETE CASCADE,
  file_id  TEXT NOT NULL REFERENCES series_files(file_id),    -- no cascade: blocks deletion (409)
  PRIMARY KEY (lid, file_id)
) WITHOUT ROWID;

CREATE TABLE access_log (
  ts         INTEGER NOT NULL,
  lid        TEXT,
  method     TEXT NOT NULL,
  path       TEXT NOT NULL,
  range      TEXT,
  status     INTEGER NOT NULL,
  bytes      INTEGER NOT NULL,
  recipient  TEXT
);
CREATE INDEX access_ts ON access_log(ts);
```

Two relationships matter:
- **`link_files.file_id` deliberately has no cascade.** Deleting a series file that some link still lists fails with a foreign key error, which the API returns as `409 Conflict`.
- **Deleting a link cascades to its `link_files` rows** in the share file, and to its `caps` rows in the catalog.

## Request flows

**`GET /shl/{lid}/{fileId}.bin` with `Range: bytes=a-b`**
1. Check the shape of `lid` and `fileId`; anything else gets `404`.
2. Catalog lookup `lid → sid`. If missing, `404`. Open (or reuse) `shares/{sid}.db`.
3. Check the link: it exists, is online and not expired, has no passcode, and has a `link_files` row for `fileId`. Otherwise `404`.
4. Read `size` from `series_files`, then clamp the range to `[0, size)` and reject multi-range requests.
5. `SELECT idx, bytes FROM series_records WHERE file_id = ? AND idx BETWEEN a/65536 AND b/65536 ORDER BY idx`.
6. Stream the rows, trimming the first and last to the requested bytes. Respond `206` with `Content-Range: bytes a-b/size`, `Content-Type: application/octet-stream`, no `Content-Encoding`, and `Access-Control-Allow-Origin: *`.
7. Append to `access_log` and notify SSE subscribers.

**`GET /shl/{lid}/bundle.jwe`.** Steps 1–3 as above, without the file check. Then return `links.bundle`, with `bundle_etag` as the `ETag` and `304` for a matching `If-None-Match`.

**`POST /shl/{lid}` (passcode).** In one transaction on the share file:

```sql
UPDATE links SET remaining_attempts = remaining_attempts - 1
 WHERE lid = ? AND remaining_attempts > 0
 RETURNING remaining_attempts;
```

- **No row returned:** the link is exhausted, so `404`.
- **A row is returned:** compare the passcode hash.
  - **Match:** restore the attempt in the same transaction, then mint a capability token and insert it into `caps` in the catalog.
  - **Mismatch:** commit and return `401` with the remaining count.

Taking an attempt before checking means concurrent wrong guesses can never exceed the limit.

**`GET /cap/{token}/…`.** Catalog lookup `token → lid → sid`, with `expires_at > now`. Then the same as the `/shl` flows, without the passcode check.

## Write flows

**Uploading a series file (`PUT /api/shares/{sid}/files/{fileId}.bin`)**
1. Authenticate: the SHA-256 of the bearer token must match `share.control_token_hash`.
2. Check the name and quota: current `SUM(size)` plus `X-Expected-Size` must fit.
3. In one transaction, insert the `series_files` row. Then read the body as a stream, cutting it into 65,536-byte records and inserting each as it arrives.
4. Stop and roll back if the body runs past the expected size or the quota.
5. At the end, check that the total equals the expected size, then commit.

Nothing is visible until the commit. In WAL mode, readers carry on during the upload. A long upload grows the WAL file, so set `journal_size_limit` and checkpoint after large commits.

**Creating a link.**
1. Insert the link and its `link_files` rows into the share file, and commit.
2. Then insert `lid → sid` into the catalog.

**Deleting a link.**
1. Delete the catalog row first. That stops routing immediately and cascades to `caps`.
2. Then delete the row in the share file, which cascades to `link_files`.

**Rule for changes that touch both files:**
- When creating, write the share file first and the catalog last.
- When deleting, write the catalog first and the share file last.

The catalog therefore never routes to something that is incomplete or already gone. Anything a crash leaves behind sits in a share file with no catalog entry pointing at it, and the startup sweep removes it.

**Expiring or deleting a share.**
1. Delete the catalog `shares` row, which cascades to its links and caps.
2. Close any open connection to the share file.
3. Delete `{sid}.db`, `{sid}.db-wal` and `{sid}.db-shm`.

## Startup sweep

On start, and periodically while running:
- delete catalog `caps` rows that have expired;
- delete expired sandbox shares, as above;
- delete any `shares/*.db` file whose `sid` has no catalog row;
- in each share file that is opened, delete `links` rows that have no catalog row.

## Connections

- **Catalog:** one connection, kept open.
- **Share files:** opened on demand and kept in an LRU (for example 64 open files). Each connection sits behind a mutex and is used from `tokio::task::spawn_blocking`.
  - With `rusqlite` this needs no async driver.
  - Large range reads should stream rows to the response instead of collecting them.
- **Pragmas on every open:** `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`.
- **Schema version:** `PRAGMA user_version`. Migrations run when a share file is opened, so old share files upgrade the first time they're used.
- **SQLite version:** `RETURNING` needs SQLite 3.35 or later. Use `rusqlite` with the `bundled` feature so the version is fixed.

Each 64 KiB record overflows into a chain of pages. That is ordinary for SQLite blobs, and reads hit the page cache. Measure range-read throughput in the Stage 2 tests before tuning `page_size`.

## Path safety that remains

There are two filesystem paths:
- `{data-dir}/catalog.db`;
- `{data-dir}/shares/{sid}.db`, where `sid` comes from a catalog row and also matches `^[A-Za-z0-9_-]{22}$`.

The data directory is resolved once at startup. The process runs as an unprivileged user that owns only that directory (mode `700`). Under systemd, also set `ProtectSystem=strict`, `ReadWritePaths={data-dir}`, `NoNewPrivileges=yes` and `PrivateTmp=yes`.

## Alternatives considered

| Option | Why not |
|---|---|
| `meta.json` per share plus loose `.bin` and `.jwe` files (the current plan) | Needs a hand-written lock and atomic rename for every state change, and a mutex for the passcode counter. `meta.json` sits beside served files, so path safety has to be enforced in code for every route. |
| One SQLite database for everything | One writer for all shares. Expired shares leave free pages that only `VACUUM` reclaims. One damaged file affects everyone. |
| SQLite for state, series as files on disk | Fastest reads, using the OS to send file data directly, and the easiest move to object storage. But it brings back filesystem paths, temp files, renames and orphan sweeps. Worth it for large studies in production; not needed at the demo's 150 MB-per-share quota. |
| Object storage (S3, R2) for series | The right choice at scale. Keep the series reads and writes behind a small storage interface (`put_records`, `read_records`, `delete_file`), so a second backend can replace `series_records` without touching routes or state. |

## Tests to add (Stage 2)

1. **Range reads:**
   - first record, last (short) record, a range spanning several records, and one starting exactly on a record boundary;
   - `Content-Range` and length are exact;
   - a multi-range request is rejected or answered with a single range.
2. **Interrupted upload:** abort mid-body; no `series_files` row is visible; the next upload succeeds.
3. **Size checks:** a body over `X-Expected-Size` or over quota is rolled back.
4. **`409`:** deleting a file a link still lists returns `409`; it succeeds once the link no longer lists it.
5. **Passcode attempts:** 10 concurrent wrong attempts against 5 allowed give exactly 5 `401`s, then `404`, including for the correct passcode.
6. **Crash between the two files:** a link row in a share file with no catalog row is unreachable and removed by the sweep.
7. **Share expiry:** the files are deleted from disk; the catalog has no rows for the share; `/shl/…` and `/cap/…` return `404`.
8. **Parallel uploads:** uploads to two different shares proceed at the same time; uploads to one share queue without errors (`busy_timeout`).
9. **Traversal:** `../`, `%2e%2e%2f`, `..%5c`, `%00`, double encoding, overlong ids, and an id that matches the pattern but isn't in the catalog all return `404`; no file outside `{data-dir}` is opened.
