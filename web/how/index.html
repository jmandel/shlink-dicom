The link

Below is the sample link and the JSON inside it. Tap a field to see what it gives whoever holds the link.

A SMART Health Link is shlink:/ followed by base64url-encoded JSON. The JSON says where the encrypted data is (url) and holds the key that decrypts it (key). Anyone who has the link can read what it points to.

In a viewer address the link comes after #. Browsers do not send that part to the server, so the server that hosts the files never receives the key.

The Bundle

        
Open the decrypted Bundle below. The highlighted series lists are where the imaging is described; tap an instance's offset to see where its bytes are.

        
The link's key decrypts one file: a FHIR Bundle, sent as a compact JWE (A256GCM, DEFLATE-compressed). It holds the Patient and one ImagingStudy per study.

        
Each series has two extra values: a random file id, which names its file on the host, and a random 32-byte key for that file. Each instance has its length in bytes. Instances are listed in the order their bytes appear in the series file, so an instance's offset is the sum of the lengths before it.

        
A client that does not know these extensions ignores them and still reads a valid FHIR study.

The series file

        
Drag the slider to pick an image. The page works out which records hold it, sends one Range request for them, and verifies what comes back. Each request appears in the list.

        
Each series is one file, {fileId}.bin, next to the Bundle. It holds the series' DICOM files end to end, encrypted in records of 65,520 bytes. On the host each record takes 65,536 bytes: the ciphertext and a 16-byte authentication tag.

        
To read plaintext bytes [a, b), the client fetches records ⌊a / 65,520⌋ to ⌊(b − 1) / 65,520⌋, which start at 65,536 times the first record's index. Record i is decrypted with nonce i, written as a 12-byte big-endian number.

        
Tap a record in the map to jump to the first image that starts in it.

Decrypt and verify

        
Pick a record and decrypt it. Turn on the switch to flip one bit of it between the network and the decryptor, and the record is refused.

        
AES-256-GCM checks each record's 16-byte tag before releasing any plaintext. A changed bit fails the check, and so does a record moved to another position, because its nonce no longer matches. A short or padded file is caught by its length, which the Bundle gives. In each case the receiver uses no bytes from the record.

        
The series key and the expected lengths come from the Bundle, which is itself encrypted and authenticated under the link's key. The series file supplies only ciphertext.

What the host sees

        
The two panes show the same requests: on one side what reached the host, on the other what this browser made of them. Tap a request to see what it carried.

        
The host stores the Bundle and the series files as ciphertext. From requests it learns the paths (with random file ids), the byte ranges and their times, the number and sizes of the files, the recipient string the client sends, and, as for any web request, the client's IP address.

        
It does not learn names, DICOM UIDs or pixels: no UID appears in a URL, and the keys are only in the link and the Bundle. File sizes and the pattern of reads can still hint at the kind of study.

        
The list on the host side is this page's own requests, with the fields the server's access log keeps. Step 6 shows the server's log itself, for a share you make.

Sharing and revocation

        
Make your own link to part of the sample, open it in a new tab, then revoke it and watch the requests fail.

        
To share only some studies, the sharer encrypts a new Bundle that lists just those, under a new link key, and tells the server which series files the new link may serve. The series files are not re-encrypted: the new Bundle carries their existing ids and keys.

        
Each link reads files under its own path. Revoking a link makes the server answer 404 for its Bundle and for every file under that path. Other links to the same files keep working.

        
The sample share is read-only, so the first step asks the server for a copy you control. The copy holds the same ciphertext, expires in 24 hours, and the server needs no key to make it.

Codecs and performance

        
See which transfer syntaxes the decoder handles in its test corpus, and time decryption and decoding of the sample in this browser.

        
The DICOM files are shared exactly as the source wrote them, compression included. A receiver therefore needs a decoder for each transfer syntax it may meet. This site decodes in Web Workers, with Rust decoders compiled to WebAssembly.

        
Each corpus case is checked against a reference decode: exact for lossless syntaxes, within a stated tolerance for lossy ones.

Build it

        
Run a complete receiver here: about 50 lines that use only fetch and WebCrypto. It resolves the sample link and returns the first image's file meta header.

        
The receiver needs no library: AES-GCM from WebCrypto, DecompressionStream for the Bundle, and HTTP Range requests. The same file runs in Node 24 and Bun.
