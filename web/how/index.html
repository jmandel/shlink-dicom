How it works

Follow one slice of a brain MRI from a link to the picture on your screen. The tour uses a real shared study and runs in your browser.

Opening the sample link…

1

The link

A SMART Health Link holds two things: where the data is, and a key to unlock it. Your browser never sends the key to the server.

The link is shlink:/ followed by JSON written in base64url (bytes spelled with letters, digits, - and _). The panel shows the JSON:

  • url: where the locked index is.
  • key: 32 random bytes that unlock it.
  • flag U: the address is the file itself, so one GET fetches it.
  • label: a name for the recipient to see.

In an address that opens a viewer, the link comes after #. That part of an address, the fragment, stays in the browser: it is not part of the request.

2

The index

Your browser downloads one small locked file, unlocks it with the key, and finds a table of contents for everything shared.

The locked file is a JWE (JSON Web Encryption): a header, a random starting value and the ciphertext, sealed with AES-256-GCM. Unlocked and unzipped, it is a FHIR Bundle, the standard format for health records.

The Bundle holds the patient and one ImagingStudy per study. For every image, the ImagingStudy gives its length in bytes. It names one file for the whole study, with that file's own key; a series added later can name a file of its own.

3

The pieces

Each study is stored as one file of small locked pieces. Your browser asks for just the pieces that hold this slice.

Drag across the pieces to choose others. Every image wholly inside your choice appears.

Each piece, called a record, holds 65,520 bytes of the original files and a 16-byte seal, so it takes 65,536 bytes on the server. The study's images sit end to end, series by series, so an image at bytes a to b is in pieces ⌊a ÷ 65,520⌋ to ⌊b ÷ 65,520⌋.

3b

What the server sees

The server that delivers the pieces can't read them. This is what it gets from your visit.

It also sees your network address and the time, as any web server does.

Each line is one request. The file names are random and the key never leaves the browser, so names, dates and pixels stay hidden. The server sees one file per study, not how many series it holds, but the pieces a viewer reads show where those images begin and end, and the sizes can hint at what kind of study it is.

For each request the server logs the time, the link, the method, the path, the range, the status, the bytes sent and the recipient name the browser gives. Step 7 shows that log for a link you make.

4

Unlocking

Each piece is sealed, so any change is detected.

The seal is AES-256-GCM. Each piece is unlocked with the file's key and a nonce (a number used once) equal to the piece's number, and must match its 16-byte tag. A changed bit fails the tag, and so does a piece moved to another place, because its nonce no longer matches. So each piece is checked on its own, as soon as it arrives.

The panel draws the slice from its pieces. Each piece holds a band of the image's rows. Locked, the band is noise; once its seal matches, the rows appear.

5

Bytes to pixels

Inside is the original scanner file. Its header says what the image is; the rest is the picture.

The header is a list of DICOM attributes, each with a numbered tag. The panel shows a few of them as stored, and where the pixels begin.

5b

A compressed image

Many scanners compress their images. Your browser decodes them itself.

The sample's images are not compressed, so this slice comes from a public research collection.

6

Fetching less

You only download what you look at.

7

Share and revoke

You can share part of what you have, and take it back.

The new link has its own key and its own index, which lists only the MRI. The pieces are not locked again: the new index names the same files, with the same file keys.

After revocation the server answers 404 (not found) for the link and for its files. Revoking stops new downloads; it can't take back what a recipient has already downloaded.
