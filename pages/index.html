A SMART Health Link to imaging, served by GitHub Pages

shlink-dicom is my draft profile for sharing complete DICOM imaging studies through SMART Health Links. This copy of its viewer and the demo link below are plain files on GitHub Pages. No code of mine runs on the server; it only has to answer byte-range requests.

Why imaging needs more than one encrypted file

A standard SMART Health Link opens one encrypted file (a JWE) holding a FHIR Bundle. For imaging that is a poor fit: a JWE is base64url-encoded, which adds a third to its size, and its one authentication tag comes at the very end, so nothing in it can be checked or shown until all of it has arrived.

In shlink-dicom the link and the Bundle stay standard. The Bundle’s ImagingStudy lists every DICOM instance with its length in bytes and names an encrypted file for the study: its DICOM files laid end to end, sealed in 64 KiB records that each carry their own tag. A viewer can fetch one slice with one Range request and check it as it arrives, from any host that serves byte ranges.

Open in the viewer

The link {{LINK}}

Opened in the viewer, the link follows view/#. Browsers never send the part after # to the server, so the key stays with you.

One slice, from link to pixels

  1. The viewer reads the key from the link, after the #.
  2. It fetches demo-links/bundle.jwe ({{BUNDLE_KB}} KB) and decrypts it with that key. Inside is an ordinary FHIR R4 Bundle, with an ImagingStudy for each study.
  3. For slice {{SLICE_N}} of MRI series {{SLICE_SERIES}}, it adds up the lengths of the images listed before it. The slice starts at byte {{SLICE_OFFSET}} of the study’s DICOM bytes and lies in records {{SLICE_RECORDS}} of the file’s {{MRI_RECORDS}}.
  4. It sends one request for demo-links/{{MRI_FILE}} with Range: {{SLICE_RANGE}}. GitHub Pages answers 206 Partial Content with those {{SLICE_RECORD_COUNT}} records.
  5. It checks each record’s AES-256-GCM tag before using its bytes, then decodes and draws the slice. A record that fails the check is not shown.

The specification covers locating records, what a host must do and notes on GitHub Pages.

How this site is built

A GitHub Actions workflow builds the viewer, fetches the DICOM files from my-health-data at commit {{SOURCE_COMMIT_SHORT}}, re-encodes the uncompressed images as lossless JPEG as the full demo does, and packs them with the project’s packer. The keys are committed in pages/demo-link.json, so every deploy makes the same files and the link does not change. The build fails if the input or the packed bytes differ from the hashes recorded there.
